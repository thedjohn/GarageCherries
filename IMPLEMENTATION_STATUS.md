- [x] **Header no longer throws 406 errors for every non-dealer/non-advertiser page load** — found via DevTools while investigating an unrelated view-count discrepancy. `components/Header.tsx`'s `resolveAuth()` checked whether the logged-in user is a dealer or advertiser using `.single()` on both `dealers` and `advertisers` — `.single()` throws a PostgREST error (`PGRST116`, surfaced as HTTP 406) whenever a query returns anything other than exactly one row, including zero rows. Since most logged-in users (buyers) are neither a dealer nor an advertiser, this fired two unnecessary 406 errors in the console on literally every page load for the majority of users. Changed both to `.maybeSingle()`, which returns `null` gracefully instead of throwing when no row matches — the same pattern already used correctly elsewhere in the codebase (e.g. `app/api/dealer/apply/route.ts`) for this exact "does this exist" check (fixed 2026-07-19)
- [x] **Fixed "Google tag has already loaded" console warning** — found in DevTools alongside the Header 406 errors above. `app/layout.tsx` loaded the Enzuzo cookie-consent script and the Google Analytics scripts in the wrong relative order for Enzuzo to properly manage/gate the Google tag. A same-strategy reorder (both scripts at `strategy="afterInteractive"`) was tested first and did **not** fix it — confirmed live that `afterInteractive` scripts are async network fetches with no cross-script execution-order guarantee, so DOM position doesn't determine load order. Fixed correctly per Next.js's own documented guidance (cookie consent managers are their listed example use case for `beforeInteractive`, while analytics tools are their listed example for `afterInteractive`, which GA already was): changed only Enzuzo's `strategy` to `beforeInteractive`. Note: the specific default consent values and whether GA is actually *blocked* pre-consent (vs. just able to receive consent signals) depend on settings in Enzuzo's own dashboard account, which is outside this codebase (fixed 2026-07-19)
- [x] **Fixed a real views-undercounting bug in `/api/admin/watcher-counts` and `/api/dealer/watcher-counts`** — found while chasing a reported 8-vs-9 views discrepancy on the admin Listings tab. Root cause confirmed via a temporary production debug log (added, checked, then reverted same session): both routes fetched raw `listing_views` rows for a batch of listings (`.select('listing_id').in('listing_id', carIds)`) and counted them in JS, with no `.limit()`/pagination — but Supabase/PostgREST caps any unbounded `.select()` at 1000 rows by default. Verified directly: the exact same query for 13 real listings returned exactly 1000 rows, while the true total (`count: 'exact'`) was 1293 — 293 real view records were being silently dropped, undercounting whichever listings' rows happened to fall outside the first 1000 returned (no `ORDER BY`, so arbitrary). Fixed by moving the counting into the database via a new `count_listing_views(p_listing_ids)` Postgres function (`GROUP BY listing_id, COUNT(*)`, migration `supabase/migrations/20260719_count_listing_views_rpc.sql`, run manually per project convention) and calling it via `.rpc()` instead of fetching raw rows — Postgres aggregates correctly regardless of row volume. Verified end-to-end against live production data: the RPC's per-listing sum now exactly matches the true total (1293), and the specific listing that was undercounted (8→9) now returns the correct count. `totalWatchers` (watchlist counts) left unchanged in both routes — same unbounded-fetch pattern, but not confirmed broken since watchlist batches are far less likely to cross 1000 rows in practice. The same latent pattern also exists in the dealer digest email and today's `/reports` fix, scoped differently (by dealer or by date) — not confirmed broken, treated as a separate future item, not bundled into this fix (fixed 2026-07-19)
- [x] **Advertiser public profile pages were 404ing for every real visitor — fixed via an RLS policy, no code change needed** — this is the new `GET /api/cron/sitemap-health` job's very first real catch, less than a day after shipping: it emailed an alert for `https://www.garagecherries.com/advertisers/mobile-auto-pros` returning 404. Since this is currently the *only* active advertiser in the database, this likely means the entire advertiser public-profile feature has never actually rendered for a real anonymous visitor — internal testing presumably happened while authenticated, which may hit different RLS rules and would fully mask an anon-only block. Fixed by adding `create policy "Public can view active advertisers" on advertisers for select to anon, authenticated using (active = true)` (run manually in Supabase's SQL Editor). Verified after the policy was applied: the anon key now reads the row correctly, and `https://www.garagecherries.com/advertisers/mobile-auto-pros` returns a real 200 with the business name rendering. Pure database fix — no application code changed (fixed 2026-07-19)
